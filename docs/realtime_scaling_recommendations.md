# Рекомендации по масштабированию realtime-функционала (WebSocket)

## 1. Вертикальное масштабирование (увеличение ресурсов)
- Для контейнера бэкенда (NestJS): поднять лимиты CPU до 2 ядер, RAM до 2 ГБ (в `docker-compose.yml` секция `deploy.resources`).
- Для контейнера AI-сервиса: CPU 1–2 ядра, RAM 2–4 ГБ (зависит от моделей).
- Для Redis: не менее 512 МБ RAM, при высоких нагрузках – выделенный кэш.

## 2. Горизонтальное масштабирование бэкенда
- Запустить 2–3 реплики бэкенда. Использовать **Redis-адаптер для Socket.IO**, чтобы управлять комнатами и соединениями между репликами.
- Перед репликами поставить балансировщик (Nginx или Traefik) с настройкой **sticky sessions** (чтобы один пользователь попадал на одну реплику).
- Пример фрагмента `docker-compose.yml`:
```yaml
backend:
  deploy:
    replicas: 3
  environment:
    - SOCKET_IO_ADAPTER=redis
    - REDIS_URL=redis://redis:6379
...
## 3. Выводы на основе анализа логов WebSocket (2026-05-06)
- При единичном пользователе задержки минимальны:
  - аутентификация WebSocket: 10–53 мс;
  - запись сообщения в БД: 16–29 мс;
  - широковещательная рассылка: 0 мс.
- Ошибок, переподключений, таймаутов не зафиксировано.
- При росте нагрузки (более 100 одновременных пользователей) необходимо горизонтальное масштабирование (п.2) и Redis‑адаптер для Socket.IO.
